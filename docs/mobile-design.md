# 모바일 앱 설계

Figma 원본:

- [Money Note Mobile App](https://www.figma.com/design/ys5W1k5bwO7YQi7sWWTZK3)

이 문서는 모바일 앱 구현 시 기준으로 삼을 화면 구조와 제품 원칙을 정리한다.

## 제품 방향

Money Note 모바일 앱은 웹 앱의 축소판이 아니다.

모바일 앱의 목적은 돈을 쓴 직후 5~10초 안에 기록하고, 현금흐름을 빠르게 보정하며, 가족 관련 정산 상태를 확인하는 것이다.

우선순위:

1. 현재 상태와 최근 입력 확인
2. 카드 알림 후보 처리와 수동 입력
3. 청구와 가족카드 정산
4. 현금흐름 관리
5. 낮은 빈도의 운영 설정

복잡한 분석, 관리 로그, 복원 같은 기능은 일상 흐름을 방해하지 않도록 설정 화면에 둔다.
모바일 앱은 서버 DB를 원본으로 사용하므로 앱 시작 시 서버에 닿지 않으면 종료 안내를 보여준다.

## 문구 원칙

모든 사용자 노출 문구는 한국어로 작성한다.

예시:

- `청구`
- `가족카드`
- `상태`
- `잔여 유동성`
- `스냅샷 다운로드`

영어 기능명을 그대로 노출하지 않는다.

## 디자인 원칙

- 카드형 화면 구조를 사용한다.
- 표를 사용하지 않는다.
- 리스트와 카드 중심으로 표시한다.
- 한 손 조작을 우선한다.
- 금액은 크게 표시한다.
- 정보 밀도는 높게 유지하되 입력 흐름은 짧게 둔다.
- 애니메이션은 최소화한다.
- 장식보다 실용성을 우선한다.

## 주 검증 기기

우선 검증 타깃은 Galaxy S23 FE / One UI 8.5다.

이 기기 기준으로 다음을 우선 확인한다.

- 한 손 입력이 불편하지 않은지
- 하단 탭과 입력 버튼이 시스템 내비게이션과 겹치지 않는지
- 알림 접근 권한 화면으로 정상 이동하는지
- 우리카드 승인 알림이 본인카드/가족카드 후보함으로 잘 분류되는지
- `최근 납치한 알림`의 우리카드/통행료 탭에서 출처별 파싱 결과와 원문을 확인할 수 있는지
- 큰 글꼴 설정에서 금액과 버튼 문구가 깨지지 않는지

## 하단 탭

하단 탭은 실제 사용 빈도에 맞춰 다섯 개를 둔다.

- 홈
- 정산
- 입력
- 현금
- 설정

좌우 스와이프와 하단 탭 선택은 같은 순서로 이동한다.

## 홈 화면

앱 실행 시 기본 화면이다.

상단에는 현재 월과 다음 요약값을 표시한다.

- 카드대금
- 월 지출
- 잔여 유동성
- 동결

그 아래에는 서버가 완성한 다음 Judgment 문구를 그대로 표시한다.

- 예산심사위원회
- 미결제 카드대금이 있을 때만 파산심사위원회

예산심사위원회 카드를 누르면 `ChatGPT에게 회계감사 받기` bottom sheet가 열린다. 카드에 표시되는 기존 Judgment 문구는 바꾸지 않는다. 실제 데이터가 존재하는 연월만 선택할 수 있고, 기본값은 서버 현재 월이다. 현재 월에 데이터가 없으면 데이터가 있는 가장 최근 월을 사용한다. 미래와 데이터가 없는 연월은 선택지에 넣지 않는다.

`회계감사 소집`은 선택 월의 본인 카드 지출, 현금흐름, 현재 남은 청구와 가족카드 내역을 기존 API에서 다시 읽어 Markdown 보고서로 묶은 뒤 Android ChatGPT 앱에 직접 공유한다. 청구는 사용일이 선택 월에 속하는 현재 미정산 항목을 별도 절에 표시하고, 서버가 투영한 실청구액의 합계와 개별 사용일·내용·원금·할인액·실청구액을 제공한다. 이 합계는 가족의 최종 부담과 회수 관계를 설명하기 위한 것으로 본인 카드 지출이나 Summary에 다시 합산하지 않는다. 보고서 생성 시점의 현금성 고정지출, 확인 여부와 무관한 카드 정기결제 템플릿, 현재 미삭제 동결 항목도 별도 참고자료로 넣되 선택 월 당시의 이력으로 표현하지 않는다. 할인액과 실결제액은 서버 응답의 투영값을 그대로 사용하며 모바일이 다시 계산하지 않는다. 보고서는 앱 전용 cache에 잠시 만들고 Money-Note로 돌아올 때 삭제한다. 앱이 그 전에 종료되어도 다음 실행 시 남은 임시 보고서를 삭제한다.

회계감사관의 역할, Money Note 데이터 해석 규칙과 출력 지침은 `mobile/assets/ai_audit_instructions.md`가 단일 원본이다. 문구 담당 에이전트는 이 파일만 수정할 수 있으며, 동적 표와 금액 조립은 `mobile/lib/src/ai_audit_report.dart`가 담당한다. 앱은 지침 파일을 번들 자산으로 읽으므로 변경 후 새 APK 빌드와 배포가 필요하다.

홈의 `알림에서 가져오기`는 우리카드 승인 후보함으로 이동한다. 최근 입력은 10건을 표시하며, 수동 입력은 하단 `입력` 탭에서 수행한다. 홈에서 별도 금액 계산이나 Judgment 생성을 하지 않는다.

## 입력 화면

현재 월 카드 지출을 등록하고 원장 전체를 확인하는 화면이다.

입력 항목:

- 사용 일자
- 사용처
- 사용항목
- 분류
- 금액
- 할인 적용 여부

- 지출 추가

목표는 사용자가 10초 안에 지출을 기록하는 것이다.

원칙:

- 입력 폼 바로 아래에서 당월 지출 전체를 조회한다.
- 표를 쓰지 않는다.
- 사용처, 사용항목, 금액, 사용일을 카드 안에 표시한다.
- 각 행의 분류, 할인 적용 여부, 실결제액을 수정하고 삭제할 수 있다.
- 교통, 하이패스, 통행료처럼 결제 정책상 눈에 띄어야 하는 항목은 작은 배지로 표시할 수 있다.

## 현금 화면

현금흐름 관리 전용 화면이다.

상단에는 현금흐름 반영액과 잔여 유동성을 표시한다.

현금 입력 카드:

- 입금/출금 전환
- 내용
- 금액
- 이달 기준 수입 여부

현금흐름 항목은 카드 형태로 표시한다.

항목 카드에는 다음 정보를 둔다.

- 발생일
- 내용
- 입금/출금 금액
- 이달 기준 수입 표시
- 삭제 버튼

표 형태는 사용하지 않는다.

## 정산 화면

상단 카드 전환으로 `청구`와 `가족카드`를 오간다.

청구 화면:

- 원금 합계
- 실청구 합계
- 공유하기
- 일괄 처리 완료
- 항목별 원금, 할인, 실청구, 삭제
- 등록 전 할인 적용 여부 선택

가족카드 화면:

- 원금 합계
- 실결제 합계
- 가족카드 혜택 상태
- 공유하기
- 일괄 처리 완료
- 등록 전 할인 적용 여부 선택

청구와 가족카드는 원장이 아니라 회수 예정 정보다. 따라서 모바일에서도 소비 통계나 유동성의 핵심 흐름처럼 보이지 않도록 분리한다.

## 설정 화면

일상 입력보다 빈도가 낮은 운영 기능을 모은 화면이다.

표시 항목:

- 카드대금
- 월 지출
- 잔여 유동성
- 동결
- 동결 금액
- 현금성 고정지출
- 카드 정기결제
- 교통카드 할인: 이번 달부터 본인카드 계산식과 월별 혜택 상태를 따를지 선택
- 월마감
- 백업 / 복원
- 설정

각 관리 항목은 별도 세부 화면으로 들어간다. 관리 기능은 접근 가능해야 하지만 일상 입력 흐름을 방해하지 않아야 한다.

현금성 고정지출 관리 화면은 활성 템플릿과 이번 달 처리된 템플릿을 구분한다. 활성 항목의 실제 출금액은 template 예정액으로 미리 채우고 사용자가 이번 주기 금액만 고쳐 확인한다. 서버가 실제액의 음수 현금흐름을 만들면 관련 영역을 다시 조회한다. 확인 취소는 생성된 현금흐름을 삭제해 원래 reserve의 미확인 상태로 되돌린다. 정기지출 자체를 해제해도 이미 기록된 현금흐름은 유지된다.

카드 정기결제 관리 화면은 template 예정 원금으로 채운 이번 실제 원금 입력과 서버가 계산한 할인·실결제 preview를 보여준다. 확인 결과는 실제 원금으로 원장에 들어가고 template 예정 원금은 다음 주기를 위해 유지된다. 월마감 화면은 미확인 현금성 고정지출과 카드 정기결제 목록을 보여준 뒤 사용자가 `그래도 월마감`을 다시 선택한 경우에만 override를 전송한다.

교통카드 할인은 현재 `자동 할인 없음`과 `본인카드와 동일` 두 상태뿐이므로 체크박스/스위치로 제공한다. 전용 교통 할인식이 생기기 전까지 존재하지 않는 세 번째 정책을 UI에 노출하지 않는다. 설정 변경은 서버 기준 현재 월부터 적용되며, 앱은 저장 후 서버 계산 결과를 다시 조회한다.

## 알림 기반 입력 보조

우리카드 승인 후보와 고속도로 통행료+ 후보는 현재 실사용 입력 보조 기능이다.

현재 Android 구현 원칙:

- 알림 리스너는 하나만 유지하고 패키지명으로 출처를 구분한다.
- 우리카드 `com.wooricard.smartapp`의 일시불 승인 알림은 로컬 후보함에 저장한다.
- 알림 수신 즉시 서버 등록은 하지 않는다.
- 사용자가 후보를 확인하고 `등록`을 눌렀을 때만 기존 API를 호출한다.
- 우리카드의 할부 승인, 파싱 실패, 광고/혜택 안내는 후보로 만들지 않고 `최근 납치한 알림`의 우리카드 원문 로그에 남긴다.
- 고속도로 통행료+ `com.ex.hipass_app` 알림은 날짜·시각을 찾은 뒤 그 뒤 구간에서 금액과 요금 확인 불가 표식을 탐색해 로컬 후보로 만든다.
- 통행료 후보는 사용처 `통행료`, 세부내역은 확인된 구간으로 채운다. 금액 미확인 후보는 빈 금액으로 남기며 등록 전 사용자가 보정한다.
- 통행료 후보는 본인 사용 또는 청구 사용으로 등록할 수 있고 할인은 적용하지 않는다.
- 출처별 원문 로그는 각각 최근 30건만 유지한다.
- 원문은 `설정 -> 최근 납치한 알림`의 `우리카드`/`통행료` 탭에서 확인한다.
- 각 원문 카드는 `packageName`, `title`, `text`, `bigText`, `subText`, `textLines`, `rawText`, 알림 key와 게시 시각 등을 표시하고 개별 공유할 수 있다.

통행료 파서는 우리카드 파서와 분리한다. 문장 전체를 한 정규식으로 고정하지 않고 날짜·시각, 금액 등 강한 표식을 독립적으로 찾은 뒤 인덱스 사이에서 구간을 읽는다. 파싱 결과는 다른 카드 후보와 같은 방식으로 사용자가 확인한 뒤에만 서버에 등록한다.
