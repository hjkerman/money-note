# IC06 monitoring 지원 계약

실행 검증 runtime은 CPython 3.12.3이다. 저장소 제품 요구는 Python >=3.12이며 이번 실행에서 다른 interpreter로 교체하거나 다른 버전의 실행 성공을 주장하지 않는다. 이후 버전에서도 할당 이름을 안전성 근거로 삼지 않는다. 공개 `get_events`와 `get_local_events`가 제공하는 현재 상태를 매번 읽는다. 필수 API를 사용할 수 없거나 일반 inspection 오류가 발생하면 `B03 monitoring state unavailable; measurement incomplete`로 획득 전에 실패한다. KeyboardInterrupt 등 BaseException은 원 예외를 보존하며 획득은 없다.

`use_tool_id`는 0..5의 사용 이름을 예약한다. 3.12.3의 `free_tool_id`는 이 이름만 해제하며 global/local mask와 callback을 보존한다. `get_events`와 `get_local_events`는 해제된 ID에도 실제 mask를 반환한다. 재사용은 기존 callback/mask를 자동 초기화하지 않는다. 실제 callback 전달과 이전 callback identity는 `semantics.py`로 확인했다. [Python 3.13 규약](https://docs.python.org/3.13/library/sys.monitoring.html)은 동일한 보존 의미다. [Python 3.14 규약](https://docs.python.org/3.14/library/sys.monitoring.html)은 free_tool_id가 새 clear_tool_id를 호출해 event/callback을 해제하도록 변경됐다. 따라서 3.14의 정상 free 직후 활성 잔존 상태는 문서상 NOT REACHABLE이다. 이번 runtime에는 clear_tool_id가 없으며 구현은 이를 호출하지 않는다. 3.14에서도 현재 getter mask가 nonzero이면 거부하고 0이면 아래 계약으로 판단하므로 할당 이름에 의존하지 않는다. 3.13/3.14 실행 검증은 하지 않았다. 다른 interpreter의 동작을 3.12.3과 동일하다고 보증하지 않는다.

B03은 custom monitoring ID를 보유하거나 예외 처리할 자체 ID가 없다. CPython의 legacy trace/profile 내부 ID는 공개 0..5 바깥이며 IC05 인계로 별도 보호한다. custom ID의 global mask가 하나라도 nonzero이거나 `OwnershipContext.__enter__`의 local mask가 nonzero이면 `B03 monitoring entry observer unsupported; measurement incomplete`로 거부한다. callback이 아직 없거나 DISABLE로 특정 위치가 비활성화됐어도 mask가 nonzero이면 이 기존 정책을 유지한다. callback을 읽는 비파괴 공개 getter가 없고 등록은 변경 API이므로 preflight는 callback 등록 상태를 바꾸지 않는다. 비활성 mask의 등록 callback, 이름만 예약된 ID, 진입과 무관한 코드의 local event는 그 이유만으로 거부하지 않는다. local mask는 global event를 가리지 않는다.

정적 unsafe configuration은 `attach`의 검사에서 inner generator 진입 전에 거부한다. reference, ACTIVE, wrapper, native hold 모두 미획득이다. 이미 존재한 다른 owner의 상태를 해제하지 않는다. 사전 검사 자체가 실제 PY_START/LINE/INSTRUCTION callback에 의해 중단되면 원 예외를 보존하며 아직 획득 의무가 없다. 원 IR06 PY_RETURN callback은 검사로 inner 진입이 거부되므로 정상 반환 event가 발생하지 않는다. 비활성화 뒤 새 정상 scope는 실제 입력을 정확히 한 번 기록해야 한다.

지원 실행은 동기 소유권 변경 전체에서 외부 monitoring 설정이 안정적이라는 전제를 갖는다. 같은 thread의 reentrant observer 및 다른 thread가 public monitoring API를 호출할 수 있고 GIL은 검사와 획득을 원자 연산으로 만들지 않는다. `ready`의 두 번째 검사는 획득 도중 관측 가능한 변경을 감지해 동일 owner를 rollback하고 explicit incomplete로 실패한다. 두 thread의 barrier 실험으로 global/local released-ID 변경을 검증했다. 이는 최초부터 unsafe인 상태의 획득 전 거부와 구분한다. 마지막 검사 뒤 반환 직전의 악의적 변경·ABA 변경·검사 getter 교체를 완전히 막는다고 주장하지 않는다. 해당 concurrent/reentrant 설정 변경은 지원하지 않으며 runner에서 monitoring 변경자를 정지하고 안정된 상태에서 다시 실행해야 한다. 타 tool에 대한 lock 협약·원자 snapshot API가 없으므로 B03 내부 lock만으로 이를 보장할 수 없다. 외부 monitoring을 끄거나 callback을 바꾸지 않는다.

근거: [Python 3.12 monitoring 규약](https://docs.python.org/3.12/library/sys.monitoring.html), [실제 CPython 3.12.3 instrumentation](https://github.com/python/cpython/blob/v3.12.3/Python/instrumentation.c). 문서의 해제·getter·local/global 합성 규약을 실제 runtime 실험과 대조했다. IR06 독립 FAIL과 IA04 OPEN 판정은 역사 증거로 보존한다. 이 계약 설명 자체를 구현 결함 교정으로 간주하지 않으며 실제 교정은 `check_monitoring`의 ID-name gate 제거다.
