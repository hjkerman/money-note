# 미래 예산 주기 전환

이 문서는 확정적으로 다가올 재정 운용 변화에 대비한 후속 작업 메모다. 현재 계산이나 Judgment 정책을 변경하는 지시가 아니다.

## 현재 상태

- 잔여 유동성은 `기본 예정 수입 - 카드대금 - 유동성 차감 고정지출 - 이자지출 - 동결 + 현금흐름 반영액`으로 계산한다.
- `현금흐름 반영액`에는 DB의 수동 보정값과 전체 기간 현금흐름 누계가 들어간다.
- 카드 결제 압박 Judgment는 해당 결제월의 `이달 기준 수입` 합계를 기준으로 남은 카드대금의 부담을 판단한다.
- 해당 수입이 없으면 `기본 예정 수입`을 fallback으로 쓴다.

이 정책은 “다음에 들어올 돈을 전제로 현재 카드 사용을 감당한다”는 운용에 맞다.

## 미래 전환 조건

다음 수입을 미리 담보로 현재 신용카드 사용을 청산하고, 현재 확보된 자금 범위 안에서만 카드를 운용하기 시작하면 결제 압박 판단 기준도 바꾼다.

전환 후 후보 정책:

> 남은 카드 결제액을 `잔여 유동성`과 비교하여 현재 예산 주기 안에서 감당 가능한지 판단한다.

이때 `이달 기준 수입`은 결제 압박의 직접 분모가 아니라 현금흐름 사실 또는 별도 수입 분석 자료로 남길 수 있다.

## 현금성 정기지출 상태 전이는 그대로 유지한다

현금성 정기지출 확인은 계산 요령이 아니라 발생한 사실의 상태 전이다.

- 확인 전: 아직 나가지 않았지만 이번 예산 주기에 약속된 `미지급 의무`
- 확인 후: 선택한 처리일에 발생한 음수 `cash_flows` 기록
- 확인 순간에는 미지급 의무 차감을 제거하고 같은 금액의 실제 현금 유출을 반영한다.
- 월마감 뒤에는 정기지출 템플릿만 다음 주기용 미확인 상태로 돌아오며, 이미 생긴 현금흐름은 남는다.

따라서 미래에 재정 운용 모델을 바꾸더라도 이 전환 API와 저장 의미는 바꾸지 않는다. 바뀌는 것은 잔여 유동성이 어떤 기간의 현금흐름과 시작 자금을 읽는지다.

## 전환 시 실제로 바꿀 것

단순히 식의 변수 이름 하나만 교체하는 작업은 아니다. 다음 네 경계를 함께 정해야 한다.

1. 예산 주기의 시작일과 종료일
2. 주기 시작 시 사용 가능한 시작 잔액 또는 전기 이월액
3. `cash_flows`를 전체 기간 누계가 아니라 해당 주기 범위로 집계하는 방법
4. `scheduled_income`을 미래 수입 약속으로 계속 더할지, 이미 확보된 시작 자금으로 대체할지

전환 후에도 미확인 현금성 정기지출은 pending obligation으로 한 번 차감하고, 확인된 항목은 주기 현금흐름에서 한 번만 차감한다. 이 불변식은 현재와 미래 모델이 공유한다.

## 변경 대상

전환 시 최소한 다음을 함께 검토한다.

1. `backend/app/services/judgment/insight.py`의 `payment_reference_income` 선택
2. 결제 압박 등급 경계와 0원·음수 잔여 유동성 처리
3. `/api/judgment/current`의 응답 shape 유지 여부
4. Judgment 문구에서 `기준 수입` 표현을 `잔여 유동성` 의미로 교체
5. `docs/domain-model.md`, `docs/architecture.md`, `docs/api.md`, `docs/test-plan.md`
6. 웹과 모바일은 서버의 완성된 Judgment만 표시하는지 재확인
7. 주기별 현금흐름 조회와 시작 잔액·이월액의 단일 진실 원천

## 결정 전에 답할 질문

- 즉시결제로 이미 빠져나간 현금이 `cash_flow_balance`에 반영된 상태에서 남은 카드대금과 비교해 이중 압박을 만들지 않는가?
- 잔여 유동성이 0 이하일 때 비율 계산 대신 어떤 절대 기준을 사용할 것인가?
- 카드 결제 batch가 없는 달에도 같은 판단 기준을 사용할 것인가?
- 기본 예정 수입과 실제 월급 입금의 중복 가능성을 먼저 해소해야 하는가?

## 안전 원칙

- 이 전환은 문구 교체가 아니라 Judgment 정책 변경으로 취급한다.
- DB 스키마나 Snapshot 형식을 바꾸지 않고 가능하면 Summary의 `remaining_liquidity`를 소비한다.
- 웹과 모바일에 별도 계산식을 추가하지 않는다.
- 기존 위험 등급을 비교하는 특성 테스트를 먼저 남기고 정책을 바꾼다.
