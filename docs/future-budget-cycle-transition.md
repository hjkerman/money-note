# 미래 예산 주기 전환

이 문서는 확정적으로 다가올 재정 운용 변화에 대비한 후속 작업 메모다. 현재 계산이나 Judgment 정책을 변경하는 지시가 아니다.

## 현재 상태

- 잔여 유동성은 `기본 예정 수입 - 카드대금 - 유동성 차감 고정지출 - 이자지출 - 동결 + 현금흐름 반영액`으로 계산한다.
- `현금흐름 반영액`에는 DB의 수동 보정값과 전체 기간 현금흐름 누계가 들어간다.
- 카드 결제 압박 Judgment는 해당 결제월의 `이달 기준 수입` 합계를 기준으로 남은 카드대금의 부담을 판단한다.
- 해당 수입이 없으면 `기본 예정 수입`을 fallback으로 쓴다.

이 정책은 “다음에 들어올 돈을 전제로 현재 카드 사용을 감당한다”는 운용에 맞다.

## 미래 전환 조건

다음 수입을 미리 담보로 현재 신용카드 사용을 청산하고, 현재 확보된 자금 범위 안에서만 카드를 운용하기 시작하면 결제 압박 판단 기준도 바꾼다.

전환 후 후보 정책:

> 남은 카드 결제액을 `잔여 유동성`과 비교하여 현재 예산 주기 안에서 감당 가능한지 판단한다.

이때 `이달 기준 수입`은 결제 압박의 직접 분모가 아니라 현금흐름 사실 또는 별도 수입 분석 자료로 남길 수 있다.

## 확정된 예산 주기 정책

- 예산 주기는 달력 월과 같다. 시작일은 매월 1일이고 종료일은 해당 월의 말일이다.
- 주기 시작 가용 재원은 설정의 `기본 예정 수입(scheduled_income)`이다.
- `scheduled_income`은 일회성 초기 잔액이 아니라 매월 반복되는 예산 재원이다. 각 예산 주기의 잔여 유동성 계산에 한 번씩 더한다.
- 미래 월의 예정 수입을 현재 주기에 미리 당겨 쓰지 않는다. 해당 월이 시작될 때 그 월의 재원으로 반영한다.
- 전월의 전체 현금흐름 누계를 새 주기 현금흐름으로 다시 더하지 않는다. 현금흐름은 `occurred_on`이 해당 월 1일~말일에 속하는 행을 그 주기의 사실로 집계한다.

따라서 미래 계산의 기본 골격은 다음과 같다.

```text
해당 월 잔여 유동성
= 해당 월 기본 예정 수입
  + 해당 월 현금흐름
  - 해당 월 카드대금
  - 아직 확인되지 않은 해당 월 고정 의무
  - 이자지출
  - 동결
```

정확한 전환 시점과 Judgment 정책은 아직 확정하지 않는다. 현재 운영 계산은 이 문서를 근거로 자동 변경하지 않는다.

## Judgment에서 나중에 결정할 것

현재 본인 앱 Judgment는 세 축을 별도로 반환한다.

- `budget`: 지출 건수·지출액·현금흐름·동결·잔여 유동성을 보는 예산심사위원회
- `credit`: 본인카드와 가족카드의 합산 한도 사용률
- `payment`: 남은 카드 결제액, 결제일까지 남은 날짜, 이달 기준 수입 또는 기본 예정 수입의 비율

예산 주기 모델을 전환할 때 다음 정책을 명시적으로 결정해야 한다.

### 1. 카드 결제 압박의 기준값

`remaining_liquidity`에는 이미 카드대금이 차감되어 있다. 따라서 남은 카드 결제액을 다시 `remaining_liquidity`로 나누면 같은 카드 의무를 두 번 평가할 수 있다. 다음 중 하나를 선택해야 한다.

- **보장 여부 방식(권장 후보)**: 잔여 유동성이 0 이상이면 카드대금을 포함한 예정 의무가 이미 재원 안에 들어온 것으로 본다. 음수이면 부족액과 결제일까지 남은 날짜로 위험도를 정한다. 남은 결제액은 문구와 절대 규모 판단에만 사용한다.
- **결제 전 가용액 방식**: 카드대금을 차감하기 전의 가용액을 별도 서버 feature로 계산하고, 남은 결제액과 비율로 비교한다. 이 경우 즉시결제 현금흐름과 남은 카드대금이 중복되지 않는 별도 계산 정의가 필요하다.

현재처럼 `이달 기준 수입`, 없으면 `scheduled_income`을 분모로 쓰는 정책을 계속 유지할지도 함께 결정한다.

### 2. 결제일 긴급도의 영향

- 같은 부족액이라도 결제일까지 14일, 5일, 2일, 당일, 연체 상태를 어떻게 구분할지 정한다.
- 잔여 유동성이 충분해도 결제일이 가까우면 경고할지, 단순 안내만 할지 정한다.
- 결제 batch가 없거나 남은 결제액이 0원일 때는 항상 `quiet`로 둘지 정한다.

### 3. 0원·음수 재원의 판정

- 잔여 유동성이 정확히 0원이면 `감당 가능하지만 여유 없음`과 `위험` 중 어느 쪽인지 정한다.
- 음수이면 비율 계산을 하지 않고 절대 부족액으로 등급을 나눌지 정한다.
- 가족에게 적자 보전을 요청해야 하는 문구를 어느 부족액·시점부터 노출할지 정한다.

### 4. 예산심사위원회와 결제 압박의 역할 분리

- `budget`은 해당 월 전체 생활 운용과 잔여 유동성을 평가하고, `payment`는 카드 결제 실행 가능성만 평가하도록 경계를 유지할지 정한다.
- 두 축이 같은 음수 잔여 유동성을 근거로 동일한 위험 문구를 반복해도 되는지 정한다.
- 현금흐름·지출 건수·동결은 반드시 해당 예산 주기 데이터만 볼지 정한다. 기본 방향은 해당 월 1일~말일이다.

### 5. 이달 기준 수입의 향후 역할

- 실제 월급을 `cash_flows.is_primary_income=1`로 기록했을 때 이것을 Judgment 참고자료로만 쓸지 정한다.
- `scheduled_income`과 실제 월급을 동시에 수입으로 평가하여 낙관적인 판단을 만들지 않도록 우선순위를 정한다.
- 실제 수입이 기본 예정 수입보다 적거나 많은 달에 Judgment가 그 차이를 지적할지 정한다.

### 6. 카드 한도와 비핵심 도메인

- `credit`은 현재처럼 본인카드와 가족카드 합산 한도 사용률을 유지할지 정한다.
- Claim 제거 후 `budget`의 claim 건수·금액 feature를 함께 제거한다.
- Family Card는 비핵심 기능이므로 향후 제거해도 `budget`, `payment`, 잔여 유동성 판단이 바뀌지 않도록 한다. `credit`에서만 최소 연결을 유지하는 방향이 자연스럽다.

정책을 결정한 뒤에는 먼저 입력 feature와 등급 경계를 테스트로 고정하고, 그다음 문구 pool을 수정한다. 문구부터 바꾸면 같은 문장이 서로 다른 재정 상태를 뜻하게 될 수 있다.

## 현금성 정기지출 상태 전이는 그대로 유지한다

현금성 정기지출 확인은 계산 요령이 아니라 발생한 사실의 상태 전이다.

- 확인 전: 아직 나가지 않았지만 이번 예산 주기에 약속된 `미지급 의무`
- 확인 후: 선택한 처리일에 발생한 음수 `cash_flows` 기록
- 확인 순간에는 미지급 의무 차감을 제거하고 같은 금액의 실제 현금 유출을 반영한다.
- 월마감 뒤에는 정기지출 템플릿만 다음 주기용 미확인 상태로 돌아오며, 이미 생긴 현금흐름은 남는다.

따라서 미래에 재정 운용 모델을 바꾸더라도 이 전환 API와 저장 의미는 바꾸지 않는다. 바뀌는 것은 잔여 유동성이 어떤 기간의 현금흐름과 시작 자금을 읽는지다.

## 전환 시 실제로 바꿀 것

단순히 식의 변수 이름 하나만 교체하는 작업은 아니다. 확정된 정책에 맞춰 다음 경계를 함께 바꾼다.

1. 서버 기준일이 속한 달의 1일과 말일을 예산 주기 경계로 계산한다.
2. `scheduled_income`을 해당 월 시작 재원으로 한 번 반영한다.
3. `cash_flows`를 전체 기간 누계가 아니라 해당 월의 `occurred_on` 범위로 집계한다.
4. 카드대금·미확인 고정 의무·이자·동결도 같은 예산 주기 의미로 정렬한다.
5. 전환 전후 금액을 실제 Snapshot 사본으로 대조하고, 월 경계 테스트를 추가한다.

전환 후에도 미확인 현금성 정기지출은 pending obligation으로 한 번 차감하고, 확인된 항목은 주기 현금흐름에서 한 번만 차감한다. 이 불변식은 현재와 미래 모델이 공유한다.

## 변경 대상

전환 시 최소한 다음을 함께 검토한다.

1. `backend/app/services/judgment/insight.py`의 `payment_reference_income` 선택
2. 결제 압박 등급 경계와 0원·음수 잔여 유동성 처리
3. `/api/judgment/current`의 응답 shape 유지 여부
4. Judgment 문구에서 `기준 수입` 표현을 `잔여 유동성` 의미로 교체
5. `docs/domain-model.md`, `docs/architecture.md`, `docs/api.md`, `docs/test-plan.md`
6. 웹과 모바일은 서버의 완성된 Judgment만 표시하는지 재확인
7. 주기별 현금흐름 조회와 시작 잔액·이월액의 단일 진실 원천

## 결정 전에 답할 질문

- 카드 결제 압박은 `보장 여부 방식`과 `결제 전 가용액 방식` 중 어느 쪽을 사용할 것인가?
- 즉시결제로 이미 빠져나간 현금이 `cash_flow_balance`에 반영된 상태에서 남은 카드대금과 비교해 이중 압박을 만들지 않는가?
- 잔여 유동성이 0 이하일 때 비율 계산 대신 어떤 절대 기준을 사용할 것인가?
- 카드 결제 batch가 없는 달에도 같은 판단 기준을 사용할 것인가?
- 실제 월급을 현금흐름에도 기록할 경우 매월 `scheduled_income`과 중복되지 않도록 어떤 입력 규칙을 둘 것인가?

## 안전 원칙

- 이 전환은 문구 교체가 아니라 Judgment 정책 변경으로 취급한다.
- DB 스키마나 Snapshot 형식을 바꾸지 않고 가능하면 Summary의 `remaining_liquidity`를 소비한다.
- 웹과 모바일에 별도 계산식을 추가하지 않는다.
- 기존 위험 등급을 비교하는 특성 테스트를 먼저 남기고 정책을 바꾼다.
