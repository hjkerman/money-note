# 개발·실험 임시 산출물 관리

개발 및 benchmark 작업은 자신이 만든 임시 산출물을 추적하고, 재현에 필요한 증거를 보존한 뒤 더 이상 필요 없는 산출물만 안전하게 정리한다. 삭제는 겉보기 중복이 아니라 처분 가능성이 확인된 경우에만 한다.

## 작업 중

- SQLite 임시 DB·복제본, 합성 workspace, backend 데이터, 중간 백업, benchmark 출력, build/test 중간물을 기록한다. 가능하면 파일을 여기저기 만들지 말고 크기가 제한된 task별 scratch 디렉터리를 사용한다.
- 큰 실험 전 예상 저장공간과 여유 디스크를 확인한다. 불필요한 전체 DB 복제와 반복 build 출력을 피하고, 성능 측정을 방해하는 지속적인 전체 디스크 검색은 하지 않는다.
- 증거 manifest가 참조하는 파일, 필수 fixture, canonical object, 일관된 backend/client SQLite snapshot 중 후속 검증에 필요한 것은 보존한다. 일관된 DB 사본이 필요하면 지원되는 SQLite backup 절차를 사용한다. 과거 Target을 matched-tail 검증 전에 삭제한 사례를 되풀이하지 않는다.

## 실험 경계에서 정리

각 실험이나 주요 검증 단계가 끝나면 다음을 수행한다.

1. 이번 작업이 만든 임시 산출물과 아직 필요한 증거를 구분한다.
2. 정리 대상이 작업 소유인지, 다른 프로세스나 Codex 세션이 사용 중이지 않은지 확인한다.
3. 활성 SQLite DB와 WAL/SHM, backend server, Flutter/Dart 작업, benchmark runner가 사용 중인 파일은 삭제하지 않는다. 사용 여부를 판단할 수 없으면 보존한다.
4. 재현에 필요한 증거를 보존하고, 처분 가능성이 확인된 이번 작업의 임시 산출물만 삭제한다.
5. 삭제 대상과 결과를 기록한다. 여러 시간짜리 캠페인 마지막까지 정리를 미루지 않는다.

## 기존 파일과 생성 캐시 보호

- 사전에 존재한 실험 파일, 미커밋 소스·테스트, Git index/history, 독립 감사 증거, 유일한 일관 DB 사본, 증거 manifest가 가리키는 대체 불가 파일은 자동 삭제하지 않는다.
- 생성 build cache는 명확히 식별되고 비활성이며 정리 권한이 있을 때만 지울 수 있다. 큰 파일이라는 이유만으로 기존 cache를 지우거나, 동시 작업의 build 디렉터리·유일한 증거를 삭제하거나, 시스템 전체 cache를 자동 purge하지 않는다. 기존 cache 정리는 명시적 승인이 있거나 작업별 정책이 허용하는 경우에만 한다.
- 파일의 소유자나 용도가 불확실하면 삭제하지 말고 정리 후보로 보고한다. 광범위한 repository cleanup 명령을 사용하지 않는다.

## 결과 보고

상당한 임시 산출물을 만든 작업은 종료 보고에 생성·삭제 항목, 대략 회수한 디스크 용량, 보존한 필수 증거, 남은 검토 대상과 정리 차단 사유를 짧게 기록한다. 큰 임시 산출물을 만들지 않은 작업은 `NOT APPLICABLE`로 표시할 수 있다.
