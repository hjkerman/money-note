## 환경과 고정 절차

- Intel Core i7-8750H, Linux x86_64, Flutter 3.47.4 / Dart 3.13.3, flutter test debug JIT·단일 worker. 독립 임시 패키지 A/B에 같은 의존성과 fixture를 사용했다. physicalSize400×800, DPR1, text scale1.0이다.
- fixture는 current expense 0/50/500/1000/5000개다. ID1…N, 같은 날짜2026-10-03, essential, 원금10000/서버 표시 실결제9880·할인120 등 고정 입력을 사용했다. 달력·Summary는 기존 baselineFixture의 고정 표시값이며 금융 정합성 fixture가 아니다. fixture 생성은 측정 밖이며 모든 비교의 fixture hash가 일치한다.
- 블록 순서는 **A→B / B→A / A→B**. 각 variant·규모·블록마다 warmup5회 후 표본20회, 총 측정600개·warmup150회다. p95는 정렬한20개 중19번째(nearest-rank)다. 최초 harness 확인용 별도 smoke는 이 표본에 포함하지 않았다.
- MeasuredScreen의 super.build 전후 Stopwatch, 전체 initial pump 전후 Stopwatch를 사용했다. 스크롤은 offset240/480/720/960/1200/960/720/480/240/0의 jumpTo+각1회pump이며 maxScrollExtent로 제한한다. gesture/frame pacing 시험은 아니다.
- 한 표본마다 화면을 분리·dispose하고 새 메모리 AppState를 사용했다. 최초 pump·스크롤 뒤 notify1회에 대한 build/전체pump도 따로 기록했다. Flutter binding의 가상 frame duration은 측정값으로 사용하지 않았다.
- 최초 baseline 뒤 harness에 dart format만 적용했다. 후속 기능 테스트 준비 보완은 benchmark 분기와 계측을 바꾸지 않았다. 최초 전체 harness SHA와 후속 SHA/계측 core의 구분을 근거에 기록했다.

## 위젯 수와 수용 기준

- 반환 list delegate에 선생성된 지출 카드 수는 **0/50/500/1000/5000 → 전 규모0개**다. 전역 VM allocation 측정이 아니라 list의 실제 eager children 검사다. 후보는 builder 호출에서 해당 행을 생성한다.
- 최초 viewport는 긴 헤더·입력 폼을 표시하여 A/B 모두 mounted/visible 지출 행0개였다. 10단계 스크롤 중 mounted 행은 양쪽 최대4개였다. viewport/cache 범위의 element build와 N개 위젯 객체 선생성을 구분한다.
- 모든 표본에서 명시 notify에 따른 화면 rebuild는1회였다. mounted/visible의 각 단계 값과 row build callback 수는 원시 표본에 있다.
- **선생성 제거·지연 범위: 통과. 1k/5k build의 세 블록 모두 개선: 실패.** 0/50행 pump·scroll p95의 각 블록 비율은 모두110% 이하였다. 최대 비율은50행 3블록 scroll의106.6725%다. 작은 목록 기준 통과가 큰 목록 기준 실패를 상쇄하지 않는다.
- sort/filter는 유지됐다. 선생성 감소만으로 이 구간의 일관된 시간 개선은 입증되지 않았다. 원인을 순수 CPU·GC·thermal 중 하나로 확정하지 않는다.

## 직접 기능 검사와 보존

- 후보 직접 기능 검사 **13/13 PASS**: 새8건과 기존5건이다. 빈 목록·동일 날짜 첫/마지막 행·스크롤 후 재생성·긴 한글/emoji·실제 category 메뉴 선택/재정렬 identity·할인 적용/제외·실결제 수정·삭제 target·pull refresh·draft/focus·single-flight/늦은 응답·Offline disabled/예상 표시·서버 표시값을 확인했다.
- 최초13건 중2건은 테스트 준비 오류(복수 Scrollable의 모호한 선택, focus 미확립)였다. 명시 Scrollable과 focus 선행 확인으로 바로잡고 다시 통과했다. 두 실패 원문도 보존했다. 금융 오계산·잘못된 mutation targeting 또는 제품 회귀로 분류할 증거는 없었다.
- 원복된 최종 화면에서 기능 **13/13**, 기존 B03/P0/adapter 보호 **29/29**, 전용 test 정적 분석, npm build, backend 합성 기능 **3/3**이 통과했다. 후보의 추가 element retention assertion은 candidate 모드에서 검증했고, 최종 baseline은 기존 mutation targeting과 동작을 검증한다. 전체 최종 감사나 전체 회귀 suite의 완료를 뜻하지 않는다.
- 기존 파일·symlink 7,929개의 내용·mode를 대조했다. 허용된 로드맵·compact 근거 외 기존 변화는0개이며 HEAD·인덱스·staged entry와 역사 근거 값을 보존했다. task-owned 임시 산출물545개, 관찰 할당량207,974,400B(약198.34MiB)를 정리하고 원시 표본·전후 소스·실패 로그는 압축 근거에 남겼다. 기존 cache·DB·증거는 삭제하지 않았다.
- 4단계 로드맵은 **성능 → 모바일 데이터 사용량 → dead code/중복 정리 → 최종 감사**로 최소 수정했다. 이후 Snapshot 확장성은 크기가 과도해질 때 다루며 이번에는 착수하지 않았다. 기존 성능 지도·과거 수치·순위는 보존했다.
